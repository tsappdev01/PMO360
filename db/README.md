# Database scripts

Every SQL script lives here, committed, so it can be pulled and run. One file per job, numbered
in the order they are applied. Nothing in this folder is generated by the application at
runtime: the schema, the procedures and the reference data are all defined here.

All data access from the portal is through the stored procedures in this folder. There is no
ORM and no ad-hoc SQL in the application, and `030_permissions.sql` grants the application
`EXECUTE` and nothing else — so a write cannot step around a business rule or the audit trail.

## Running them

In order, against the PMO360 database. Every script is re-runnable: DDL is guarded with
`IF OBJECT_ID(...) IS NULL` and `sys.indexes`, inserts are guarded with `NOT EXISTS` or written
as a `MERGE`, and procedures use `CREATE OR ALTER`. `CREATE SCHEMA` and each `CREATE INDEX` sit
in their own `GO` batch, because a batch aborts on error and takes the rest of the batch with it.

| Script | What it does |
| --- | --- |
| `001_schema.sql` | Tables, keys, check constraints and indexes. |
| `002_controlled_values.sql` | The controlled value lists (FR-02, BR-01). Ids are fixed and mirror the enums in `PMO360.Domain.Enums`. |
| `003_reference_data.sql` | Reporting entities, departments, phases and consultants. |
| `010_functions.sql` | `fn_VisibleProjects` (the section 6 scope), `fn_NextMilestone` (FR-07), the audit writer and the reference/enumeration readers. |
| `011_procs_project.sql` | Portfolio search and the standard views, project detail, create, close, reopen, particulars and assignments. |
| `012_procs_update.sql` | The update form's defaults, draft and submission — with the section 5.2 business rules. |
| `013_procs_milestone_risk.sql` | Milestones (FR-06 to FR-08) and the risk and issue register (FR-09, FR-10). |
| `014_procs_dashboard.sql` | The management dashboard and the FR-23 views. |
| `015_procs_attachment_notification.sql` | Supporting documents, and the data behind WF-01 to WF-08. |
| `020_views_powerbi.sql` | The reporting views Power BI reads (section 5.4). |
| `030_permissions.sql` | The application and Power BI principals and their rights. Set the two principal names first. |

With `sqlcmd`:

```bash
for f in 001_schema.sql 002_controlled_values.sql 003_reference_data.sql \
         010_functions.sql 011_procs_project.sql 012_procs_update.sql \
         013_procs_milestone_risk.sql 014_procs_dashboard.sql \
         015_procs_attachment_notification.sql 020_views_powerbi.sql; do
  sqlcmd -S "$SQL_SERVER" -d PMO360 -G -i "$f" -b || break
done
```

`-G` authenticates with Entra ID. `-b` stops on the first error, so a failure is not buried under
the scripts that follow it. Run `030_permissions.sql` separately, once the principal names in it
are right for the environment.

The procedures in `011` call procedures defined in `013` and `015`. SQL Server resolves those
names when the procedure runs, not when it is created, so the order above is fine — but all the
scripts must be applied before the portal is started.

## Two things to keep in step

**The controlled value lists and the C# enums.** `002_controlled_values.sql` fixes the ids, and
`PMO360.Domain.Enums` mirrors them. The portal compares the two at startup through
`usp_System_GetEnumerations` and refuses to run on a mismatch, naming what is wrong — so a script
that was not applied shows as a clear message rather than as a wrong dashboard.

**The reporting cycle.** BR-06 uses the agreed cycle in three places: the portal's
`Portal:UpdateCycleDays` setting, the procedures' `@UpdateCycleDays` parameter (which the portal
passes), and the `IsNotReported` column in `020_views_powerbi.sql`, which hard-codes 7 because a
view takes no parameters. If the business confirms a figure other than 7, change the setting and
that view together.

## Adding a department, a vendor or a phase

Reference data is data. Add the row to `003_reference_data.sql`, commit it, and run the script
against each environment — the inserts are guarded, so re-running adds what is missing and leaves
what is already there, including anything the PMO has added by hand. It must be changeable
without a rebuild and a redeploy, which is why the application never seeds it.
